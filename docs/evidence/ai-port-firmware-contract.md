# AI Port firmware and first native discovery result

This is an interface record for issue [#6](https://github.com/Olli0103/unifi-ai-key-emulator/issues/6). It does not include vendor code, firmware, credentials or camera media. The existing-device reconnect result below does not prove fresh management-token adoption.

The package from the catalog's [official download URL](https://fw-download.ubnt.com/data/AI-Port/4dcc-all-5.1.12-8f4dc4b3-0aa7-4c3f-90d3-8aa4c568f29b.bin) matched that hash. It was inspected as data in temporary storage. No vendor binary was executed or added to this repository.

Protect 7.2.105's request helper logs in to a device with `POST /api/1.2/login`, using the current username and plain password, then carries a session cookie on later authenticated requests. Its `UpdateUsernamePassword` command carries a SHA-512 crypt hash of the new password. These static interface observations guided an independent implementation of private credential persistence and login. Protect's next command after the live rotation reply is now observed; native HTTPS login is still `needs_evidence`.

The initial discovery probe used a newly generated locally administered MAC and self-signed certificate, separate from the existing AI Key. It sent no token, default password, camera stream or model request. The later, separately gated stream trials are recorded above. Private instance configuration is not included in the public repository because it carries local addresses and a certificate pin.

An adopted, no-camera reconnect still counted one unknown controller request after the settings handshake. A four-minute probe retained only a short hash of its function name in memory. Matching that hash against names in the inspected controller package identified `UpdateFaceDBRequest`. Protect 7.2.105's recognition handler sends this command to connected AI Ports with a private face-database URL. The probe was removed and the container restarted with no diagnostic flags. A new candidate answered the next native request with an explicit unsupported status without fetching or echoing its payload; pinned health counted one response, and Protect still showed the AI Port Online. This identifies a face-database command, not proof that face recognition works. Protect gave no explicit acknowledgement of the unsupported result, so its handling and actual face recognition remain `needs_evidence`.

## Smart-event ingress gate

Static Protect 7.2.105 module `29116` associates an AI Port message with a paired camera by matching `payload.deviceID` to that camera's MAC. It routes `EventSmartDetect` edges `enter`, `moving`, `leave` and `none` to the original camera's event handlers, subject to the controller's normal filters. The same module maps per-camera `EventAIPortStatus.isSmartDetectReady` to smart-service readiness. Module `36276` sends enhanced-motion and smart-detection settings only when the paired stream is running and readiness changes to true; module `20274` builds a `ChangeSmartDetectSettings` payload for the AI Port when the camera supports smart detection. These are interface observations from a different Protect version, not live proof that 7.3.60 persists an emulated event.

The current candidate reports streaming only after a decoded frame and always reports smart and audio readiness false. It does not emit `EventSmartDetect`. The next native check needs a detector and a validated settings handler, followed by one consented real detection that appears on the original camera timeline and a verified native test alarm. Setting readiness true or showing an AI badge without that result would be a false parity claim. Protect 7.3.60 payload acceptance, timestamps, event end handling and recording association remain `needs_evidence`.

## Capacity and container listeners

[Ubiquiti's AI Port FAQ](https://help.ui.com/hc/en-us/articles/28315005177239-Protect-AI-Port-FAQs) gives per-device limits by source and resolution and forbids mixing ONVIF and Protect cameras on one AI Port. The independently written `aikey.aiport_deployment` planner reads the existing private camera preflight, groups connected legacy cameras by source, and reserves capacity using those published limits. If the inventory lacks resolution, it reserves 4K capacity until the stream dimensions are verified. It never auto-pairs a camera.

Every planned AI Port needs its own identity, persistent state and reachable host IP. HTTPS 443 is a **fixed listener per AI Port instance**, not a new TCP port for each camera. The existing AI Key keeps its own HTTPS 8080 listener. A host-side UDP 10001 responder can cover multiple identities if discovery proves necessary, since Apple container's published UDP port does not deliver the LAN multicast sender reliably. The observed outbound controller WebSocket uses TCP 7442, and the tested Protect-camera stream uses outbound RTSP on TCP 7447. Plan schema v2 reports TCP 7447 only for Protect legacy cameras; ONVIF stream ports and any additional listeners remain `needs_evidence`. The planner does not claim a complete publish list before those are verified.

Run the read-only planner with an inventory from `local-aikey inventory`:

```sh
local-aiport-plan --inventory PRIVATE_CAMERA_PREFLIGHT_JSON \
  --ai-key-ip AI_KEY_LAN_IP --ai-port-ip FIRST_AI_PORT_LAN_IP
```

For current automatic camera detection, the planner can fetch Protect's validated inventory directly through the pinned, read-only integration API:

```sh
local-aiport-plan --controller CONSOLE_PRIVATE_IPV4 \
  --api-key-file PRIVATE_PROTECT_API_KEY_FILE \
  --web-trust-file PRIVATE_WEB_TRUST_JSON \
  --web-cert-file PRIVATE_PINNED_WEB_CERT \
  --ai-key-ip AI_KEY_LAN_IP --ai-port-ip FIRST_AI_PORT_LAN_IP
```

The JSON names the number of instances and Apple container TCP publish bindings. Unassigned instances have no binding, so a deployment controller must refuse to start them until it has distinct, conflict-checked IPs. A container cannot add host-published ports to itself after startup; a host deployment controller must refresh inventory and create or reconcile the required instances. The current planner and unadopted candidate are not yet a functional AI Port profile or an automatic container launcher.

The [isolated candidate service](../aiport-candidate.md) supplies HTTPS management, a persistent device WebSocket and opt-in, time-bounded single-camera stream intake. It still lacks a permanent host 443 publish and a production multi-camera stream service. Frame counters and a small allowlist of command names retain neither frame bodies nor credentials. The management endpoint remains relevant to fresh adoption and needs a separate diagnostic. Camera pairing waits for a decoded frame and an accepted stream-control response. [Ubiquiti's port reference](https://help.ui.com/hc/en-us/articles/218506997-Required-Ports-Reference) identifies 7447 as RTSP output; the live Flur trial decoded video through that outbound connection.
